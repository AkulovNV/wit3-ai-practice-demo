# Демо занятия 1: gateway и первый агент

Два демо на стенде: запрос через gateway (≈20 минут) и агент с одним тулом (≈15 минут).
Все команды запускаются из корня репозитория. Цифры в разделах «Что должно получиться» — из прогона 22.11.26
на Mac M-series (Ollama на GPU). У 7B-модели ответы и числа токенов будут немного другими, а на CPU всё в разы медленнее.

## Подготовка

### Что должно быть запущено

Для обоих демо хватает gateway, Langfuse и демо-сервиса. Grafana, Prometheus, Loki, Gitea и Open WebUI не нужны.

```bash
docker compose up -d litellm langfuse langfuse-worker demo-api   # Postgres, ClickHouse, Redis, MinIO поднимутся сами
docker compose run --rm tools python setup.py                    # ключи LiteLLM + тестовый запрос
```

Такой набор занимает около 3 GB памяти вместо ~4.5 GB у полного стенда, поэтому подходит, если памяти мало.
`setup.py` при этом пишет «Gitea не запущена — пропускаю», это нормально.
Полный стенд (`./scripts/up.sh`) тоже годится.


### Ollama

- Ollama должна быть запущена: `curl localhost:11434/api/version`.
- По умолчанию Ollama выгружает модель через 5 минут простоя, и следующий запрос ждёт загрузки (на Mac ~8 с,
  на CPU 10–30 с и дольше). Чтобы пауз не было, запусти Ollama с `OLLAMA_KEEP_ALIVE=2h`
  или прогревай модели прямо перед каждым демо (команда ниже).
- Ollama в WSL слушает только `127.0.0.1`, и LiteLLM из контейнера получает `APIConnectionError`.
  Нужен `OLLAMA_HOST=0.0.0.0:11434` в окружении сервиса (systemd override для `ollama.service`).

### Если модели и контекст меньше, чем в репо

Демо рассчитано на `qwen2.5-coder:7b`, `qwen2.5:7b` и `num_ctx: 8192` из `config/litellm.yaml`.
Если у тебя 3B-модели или уменьшенный контекст:

- демо 1 работает целиком, меняются только числа и качество ответов;
- демо 2 требует модель с tool calling (`qwen2.5:3b` подходит, coder-версии нет) за алиасом `local-general`;
- шагу 4 демо 2 нужно окно не меньше ~3000 токенов: на втором шаге агента в модель уходит 2455 токенов.
  При меньшем окне Ollama молча обрежет сам запрос, и ошибка будет другой.

### Прогрев и функция `ask`

```bash
for m in local-coder local-general; do
  curl -s http://localhost:4000/v1/chat/completions \
    -H "Authorization: Bearer sk-mentee-wit3-local" -H "Content-Type: application/json" \
    -d "{\"model\":\"$m\",\"messages\":[{\"role\":\"user\",\"content\":\"ok\"}]}" \
    | jq -r '.choices[0].message.content'
done
```

`ask` отправляет тело запроса на gateway и печатает только ответ (или текст ошибки) и счётчик токенов.
Ключ берётся из переменной `KEY`, по умолчанию это ключ менти.

```bash
ask() {
  curl -s http://localhost:4000/v1/chat/completions \
    -H "Authorization: Bearer ${KEY:-sk-mentee-wit3-local}" \
    -H "Content-Type: application/json" -d "$1" \
  | jq '{answer: (.choices[0].message.content // .error.message), usage}'
}
```

### Сбросить расход ключа с лимитами

Перед демо и после него, иначе шаг 5 сразу упрётся в исчерпанный бюджет:

```bash
curl -s http://localhost:4000/key/update \
  -H "Authorization: Bearer sk-master-wit3-local" -H "Content-Type: application/json" \
  -d '{"key":"sk-limited-wit3-demo","spend":0,"max_budget":0.001}' | jq '{key_alias, spend, max_budget}'
```

Сброс действует сразу. `max_budget` в той же команде выставляет бюджет $0.001, если ключ создан раньше с $0.002. Лимит запросов сбрасывается сам через минуту.

### Что открыть заранее

- Langfuse → Tracing: http://localhost:3001 (`admin@wit3.local` / `wit3-admin`)
- UI LiteLLM → Virtual Keys: http://localhost:4000/ui (`admin` / `sk-master-wit3-local`)
- в редакторе: `config/litellm.yaml` и `tools/agent.py`

## Демо 1. Запрос через gateway

Цель: увидеть в цифрах токены, отсутствие памяти, температуру, лимиты и алиасы.

### Шаг 1. Запрос через curl

```bash
ask '{"model":"local-coder","messages":[{"role":"user","content":"Объясни в двух предложениях, что такое индекс в Postgres"}]}'
```

Что должно получиться: `answer` с двумя предложениями и `usage`: 46 входных токенов, 85 выходных, ~4 секунды.

На что смотреть:
- в запросе три вещи: ключ в заголовке, имя модели и массив `messages`;
- в вопросе 9 слов, а входных токенов 46. Около 30 из них — служебная обвязка чата, которую добавляет
  шаблон модели (запрос из одного слова `hi` стоит 30 токенов). Остальное — русский текст, где на слово уходит 2–3 токена.

### Шаг 2. Тот же запрос в Langfuse

Langfuse → Tracing → верхняя запись. Она появляется через 10–30 секунд после запроса.
Запросы через curl называются `litellm:mentee` (по алиасу ключа).

Что показать по порядку:
1. Input и Output: ровно то, что ушло в модель и вернулось.
2. Модель: клиент просил `local-coder`, в трейсе реальная `ollama_chat/qwen2.5-coder:7b`.
3. Токены: те же 46 и 85, что в `usage`.
4. Латентность в секундах.
5. Стоимость: $0.000216 = 46 × $0.000001 + 85 × $0.000002. Цена условная, из `model_info` в `config/litellm.yaml`.

В клиенте ничего не настраивалось: трейс записал gateway.

### Шаг 3. Памяти нет

```bash
ask '{"model":"local-coder","messages":[{"role":"user","content":"Меня зовут Маргарита. Запомни это."}]}'
ask '{"model":"local-coder","messages":[{"role":"user","content":"Как меня зовут?"}]}'
```

Что должно получиться: на первый запрос модель обещает помнить имя, на второй отвечает,
что имени ей не называли, или подставляет заглушку вроде «Вы зовут [Ваше Имя]». Входных токенов во втором запросе 35.

Теперь то, что делает любой чат-клиент: вся история в одном запросе.

```bash
ask '{"model":"local-coder","messages":[{"role":"user","content":"Меня зовут Маргарита. Запомни это."},{"role":"assistant","content":"Запомнил, Маргарита."},{"role":"user","content":"Как меня зовут?"}]}'
```

Что должно получиться: модель называет имя, входных токенов уже 73 вместо 35.
Память чата живёт в клиенте, и за неё платят: история отправляется заново с каждым сообщением.

### Шаг 4. Temperature (можно пропустить)

```bash
for t in 0 0 1.5 1.5; do
  ask "{\"model\":\"local-coder\",\"temperature\":$t,\"messages\":[{\"role\":\"user\",\"content\":\"Придумай название для кофейни. Ответь одним названием.\"}]}"
done
```

Что должно получиться: при `0` два одинаковых ответа («Кофе уголь» оба раза). При `1.5` ответы разные,
например «Caffeinated Oasis» и «Brewed Bliss»: вопрос русский, а названия часто английские.
Иногда модель при этом ещё и нарушает формат: в одном из прогонов вместо одного названия пришёл список из десяти.
Высокая температура уводит от самого вероятного продолжения, и страдает не только выбор слов, но и язык и следование инструкции.

### Шаг 5. Лимиты и бюджет

Второй ключ: 2 запроса в минуту, бюджет $0.001.

```bash
export KEY=sk-limited-wit3-demo
for i in 1 2 3; do ask '{"model":"local-coder","messages":[{"role":"user","content":"Привет"}]}'; done
```

Что должно получиться: два ответа, на третий запрос
`Rate limit exceeded for api_key: … Limit type: requests. Current limit: 2, Remaining: 0. Limit resets at: …`.

Пока идёт минута до сброса лимита: UI LiteLLM → Virtual Keys, ключи `mentee` и `limited-demo` с бюджетом,
лимитом и расходом. В Langfuse отклонённые запросы тоже видны: записи `litellm:limited-demo` без токенов и стоимости.

Бюджет. Запрос идёт ~50 секунд на Mac и заметно дольше на CPU:

```bash
ask '{"model":"local-coder","max_tokens":1500,"messages":[{"role":"user","content":"Напиши подробное эссе на 1000 слов о пользе код-ревью"}]}'
```

Что должно получиться: 850–1200 выходных токенов (длина гуляет от прогона к прогону), это $0.0017–0.0025 при бюджете $0.001.
Бюджет исчерпывается уже на ~500 выходных токенах, так что запас двукратный.

Подожди 10 секунд (расход записывается асинхронно) и повтори короткий запрос:

```bash
ask '{"model":"local-coder","messages":[{"role":"user","content":"Привет"}]}'
unset KEY
```

Что должно получиться: `Budget has been exceeded! Key=limited-demo (sk-...demo) Current cost: 0.0019…, Max budget: 0.001`.
Если запрос прошёл, расход ещё не записался: подожди минуту из-за лимита запросов и повтори.

Не забудь `unset KEY`, иначе шаг 6 пойдёт под ограниченным ключом.

### Шаг 6. Алиасы моделей

Открой `config/litellm.yaml`, раздел `model_list`: клиенты знают только имена `local-coder` и `local-general`.

```bash
ask '{"model":"local-general","messages":[{"role":"user","content":"Объясни в двух предложениях, что такое индекс в Postgres"}]}'
```

Что должно получиться: тот же вопрос, что в шаге 1, тот же адрес и ключ, другой ответ (46 входных токенов, 101 выходной).
В Langfuse у этого запроса модель `ollama_chat/qwen2.5:7b`.

## Демо 2. Первый агент

Цель: увидеть, что агент — это цикл и описание тула, и по трейсу объяснить его ответ, в том числе неправильный.

### Шаг 1. Запуск агента

```bash
docker compose run --rm tools python agent.py "Какие отзывы оставили на товар 1?"
```

Что должно получиться (6–10 секунд):

```
tools: demo_api_get
→ demo_api_get({"path": "/products/1/reviews"})
   HTTP 200
   [{"id":1,"author":"boris","text":"Отличная клавиатура, щёлкает приятно."},{"id":2,"author":"vera",…}]

На товар с id 1 оставили следующие отзывы:
1. boris написал: "Отличная клавиатура, щёлкает приятно."
2. vera написала: "Доставили быстро, всё работает."
```

Строка `tools:` — что агенту доступно. Строка со стрелкой — модель попросила вызвать тул.
Под ней ответ сервиса: вызов сделал скрипт, а не модель. Последний блок — финальный ответ.

### Шаг 2. Код агента

В `tools/agent.py` три места:

1. `HTTP_TOOL`: имя, описание и JSON-схема параметров. Это всё, что модель знает о сервисе.
   Список эндпоинтов в описании написан руками; убери оттуда отзывы, и агент перестанет их находить.
2. Цикл `for step in range(args.max_steps)`: вызов модели, проверка `tool_calls`, выполнение тула,
   добавление результата в `messages` с ролью `tool`. Весь агент здесь.
3. Три ограничения: `--max-steps` (чтобы не зациклился), `ALLOWED_TOOLS` (список разрешённых тулов)
   и `trace_id` (все шаги складываются в один трейс).

Вопрос для обсуждения: где в этом коде можно запретить агенту опасное действие?

### Шаг 3. Трейс в Langfuse

Langfuse → Tracing → трейс `agent`, внутри два вызова модели:

| | Input | Output | Входных токенов |
|---|---|---|---|
| `step-0` | системный промпт, вопрос, описание тула | текста нет, только `tool_call` | 271 |
| `step-1` | всё то же + сообщение ассистента с вызовом + сообщение с ролью `tool` с JSON от сервиса | финальный текст | 372 |

Модель не помнит, что вызывала тул: на втором шаге ей заново прислали весь разговор,
и результат тула лежит в нём как обычный текст. Каждый шаг агента дороже предыдущего.

### Шаг 4. Уверенная ошибка

```bash
docker compose run --rm tools python agent.py "Сколько всего заказов у пользователя 2?"
```

Что должно получиться: агент вызывает `/users/2/orders` и уверенно отвечает
«У пользователя с ID 2 всего 82 заказа» (три прогона подряд дали 82). Правильный ответ — 1000:

```bash
docker compose exec -T postgres psql -U shop shop -c "select count(*) from orders where user_id=2"
```

Причину ищем в трейсе:

1. `step-1` → сообщение с ролью `tool`: JSON обрывается на середине заказа. Входных токенов 2455 против 271 у `step-0`.
2. В `agent.py` результат тула обрезается: `out[:4000]`. Сервис вернул 140 000 символов, модель увидела первые 4000.
3. В эти 4000 символов поместилось 28 заказов. Последний целый заказ в обрезанном куске имеет `"id":82`:
   модель выдала идентификатор за количество и не написала, что видит только часть данных.

Здесь сразу два термина: конечное окно и галлюцинация.
Как чинить: тул отдаёт агрегат (эндпоинт со счётчиком), тул отдаёт данные постранично, либо агенту дают другой тул.
На занятии 2 агент получит доступ к базе через MCP и сделает `SELECT count(*)`.

### Шаг 5. Тула нет (можно пропустить)

```bash
docker compose run --rm tools python agent.py "Какой сейчас RPS у сервиса и есть ли ошибки?"
```

Что должно получиться: в прогоне агент не вызвал ни одного тула и честно ответил, что по API эту информацию
не получить и нужен мониторинг или логи. Возможны и другие исходы: вызов `/health` с выводом из него или выдуманные цифры.
На занятии 2 агент получит Prometheus и логи через MCP.

### Если осталось время: модель имеет значение

```bash
docker compose run --rm tools python agent.py --model local-coder "Какие отзывы оставили на товар 1?"
```

Что должно получиться:

```
tools: demo_api_get

{"name": "demo_api_get", "arguments": {}}
```

`local-coder` пишет вызов тула текстом вместо структурированного `tool_call`, поэтому цикл завершается без вызова.
Tool use поддерживают не все модели, для агента на стенде отдельный алиас `local-general`.
Тот же эффект в Open WebUI: с включёнными Builtin Tools `local-coder` отвечает на обычный вопрос JSON-ом вида
`{"name": "search_calendar_events", …}`. Лечится выключением Builtin Tools для этой модели.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Запрос висит дольше 30 секунд | Модель выгрузилась и грузится заново. Подожди; на будущее см. `OLLAMA_KEEP_ALIVE` в подготовке |
| `APIConnectionError` / `Connection refused` от LiteLLM к Ollama | Ollama не запущена (`brew services start ollama`) или слушает только `127.0.0.1` в WSL (`OLLAMA_HOST=0.0.0.0:11434`) |
| Трейса нет в Langfuse | Запись асинхронная, подожди 30 секунд и обнови. Если нет совсем: `docker compose logs litellm \| grep -i langfuse` |
| Третий запрос ограниченным ключом прошёл без 429 | Запросы попали в разные минуты. Повтори цикл из трёх запросов подряд |
| Бюджет не срабатывает | Расход ещё не записан: подожди минуту и повтори. Проверь бюджет ключа в UI LiteLLM: должен быть $0.001, иначе выполни команду сброса из подготовки |
| `Budget has been exceeded` сразу на первом запросе шага 5 | Расход остался с прошлого раза: команда сброса из подготовки |
| `Invalid API key` у `sk-limited-wit3-demo` | Ключ удалён: `docker compose run --rm tools python setup.py` создаст его заново |
| Агент падает или молчит | Запусти ещё раз: 7B-модель нестабильна. Запасной вариант: `--model cloud` |
| Агент дал другой ответ, чем здесь | Открой трейс и разбери, почему: ради этого навыка всё демо |
| Стенд лёг целиком | `docker compose ps`, затем `./scripts/up.sh`: он идемпотентный |
