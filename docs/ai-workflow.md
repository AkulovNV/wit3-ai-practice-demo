# Личный AI-workflow: гайд

Как встроить AI-ассистента в ежедневную разработку и не потерять контроль над кодом.
Гайд к ДЗ занятия 1: прочитать, выбрать инструменты, две недели поработать по этим практикам и вести лог (раздел 9).

Главная мысль: **AI ускоряет набор кода, а ответственность за код остаётся на вас.**
Все практики ниже нужны, чтобы ускорение не превратилось в долг: непонятный код, сломанные тесты, утёкшие секреты.

---

## 1. Инструменты: три класса

| Класс | Примеры | Для чего хорош | Где слаб |
|---|---|---|---|
| **IDE-ассистент** | Cursor, GitHub Copilot, JetBrains AI / Junie, Continue | автодополнение, правка выделенного фрагмента, вопросы по открытому файлу | большие изменения через много файлов |
| **CLI-агент** | Claude Code, Aider, Codex CLI, Gemini CLI | задачи «под ключ»: прочитать репо, спланировать, поправить несколько файлов, запустить тесты | легко получить большой дифф, который вы не прочитали |
| **Чат** | Claude, ChatGPT, Open WebUI на стенде | разобраться в теме, обсудить дизайн, набросать SQL или регулярку, разобрать стектрейс | не видит ваш код, только то, что вы вставили |

Как выбирать:
- **Знаете, что писать, и это пара строк** — автодополнение в IDE.
- **Понятная задача на несколько файлов** (фича, рефакторинг, тесты) — CLI-агент.
- **Ещё не знаете, что делать** — чат: сначала разобраться, потом писать.

Начните с одного IDE-ассистента и одного CLI-агента. Пять инструментов сразу — это настройка, а не работа.

**Если внешние модели запрещены политикой компании**, работайте так же, но на локальных моделях.
Ollama + Continue / Aider через свой gateway — ровно то, что собрано на стенде (README → «IDE-ассистент через gateway»).
Локальная 7B-модель слабее облачной: давайте ей задачи меньше и проверяйте внимательнее.
**До подключения любого инструмента к рабочему коду** узнайте политику компании: какие инструменты разрешены и какой код и данные можно отправлять наружу.

## 2. Основной цикл: план → согласование → реализация → проверка

Самая частая ошибка — сразу написать «сделай фичу X». Агент сделает: как-то, где-то, со своими допущениями.

1. **План.** Попросите агента изучить код и предложить план без правок кода.
   > Изучи, как устроены заказы в сервисе. Предложи план, как добавить отмену заказа: какие файлы изменишь, какие edge cases видишь, какие тесты добавишь. Код пока не пиши.

   В Claude Code для этого есть plan mode (Shift+Tab), в Aider — режимы `/ask` и `/architect`.
2. **Согласование.** Прочитайте план как ревью дизайна. Поправьте допущения («возвращать деньги не нужно, только статус»), уберите лишнее («кэш не нужен»). Это дешевле всего: пока не написано ни строчки.
3. **Реализация.** Только теперь — «делай по плану». Большую задачу делите на шаги и проверяйте каждый.
4. **Проверка.** Тесты, линтер и чтение диффа (раздел 6). Не «агент сказал, что всё работает».

Правило: **если не можете объяснить план своими словами, не давайте его реализовывать.**

---

## 3. Файл правил проекта

Агент каждый раз начинает с нуля. Чтобы не объяснять одно и то же, правила проекта кладут в файл в корне репо:

| Инструмент | Файл |
|---|---|
| Claude Code | `CLAUDE.md` |
| Codex CLI, Cursor, Copilot и другие | `AGENTS.md` (общий стандарт) |
| Gemini CLI | `GEMINI.md` |
| Cursor / Copilot / Continue (своё) | `.cursor/rules/`, `.github/copilot-instructions.md`, `.continue/rules/` |

Что туда писать: только то, что нельзя быстро понять из кода.

```markdown
# Проект: orders-service

## Команды
- Тесты: `make test` (один файл: `pytest tests/test_orders.py -x`)
- Линтер: `make lint` — запускать перед коммитом

## Правила
- Python 3.12, FastAPI, SQLAlchemy 2.0 (async). Без новых зависимостей без согласования.
- Деньги — только Decimal. Время — только UTC.
- Миграции через alembic, руками схему не менять.
- Не трогать `legacy/` — его выпиливает другая команда.

## Как работать
- Сначала план, потом код. Маленькие коммиты.
- Не менять существующие тесты, чтобы они прошли. Если тест неверный — сказать об этом.
```

Советы:
- Коротко: 30–80 строк. Длинный файл съедает контекст, и модель следует ему хуже.
- Пополняйте файл каждый раз, когда поправили агента второй раз за одно и то же.
- Файл коммитится в репо и помогает всей команде, в том числе людям.
- В Claude Code `/init` создаст черновик по коду репо — дальше его надо вычистить руками.

## 4. Маленькие диффы и частые коммиты

Git — ваша кнопка «отменить» для агента.

- **Перед запуском агента — чистое рабочее дерево** (`git status`). Тогда всё, что он сделал, видно одним `git diff`, а откатить можно через `git restore .` (это удаляет незакоммиченные правки — откатываете только работу агента).
- **Одна задача — один небольшой коммит.** Дифф на 50 строк вы прочитаете, на 800 — нет.
- **Хороший шаг сразу коммитьте**, прежде чем просить следующий. Aider делает это сам: каждое изменение — отдельный коммит.
- **Агент пошёл не туда** — не уговаривайте его исправить. Откатитесь и переформулируйте задачу. Это быстрее.
- Длинная сессия деградирует: контекст забит старыми попытками. Новая задача — новая сессия.

## 5. Тесты как контракт

Тесты — способ сказать агенту «что значит готово» и проверить результат без доверия к нему.

- **Сначала тесты.** Попросите написать тесты на нужное поведение, прочитайте их, согласуйте — потом реализация.
  > Напиши тесты на отмену заказа: отмена нового заказа, отмена отправленного (ошибка), повторная отмена. Реализацию не пиши.
- **Агент не меняет тесты, чтобы они прошли.** Правки в тестах при реализации фичи — красный флаг: смотрите их первыми.
- Проверьте, что тест реально падает без реализации. Тест, который проходит всегда, ничего не проверяет.
- Красный тест после правки — хороший сигнал для агента: дайте ему вывод теста, и он часто исправится сам.

## 6. Читать каждый дифф

Код, который вы не читали, нельзя коммитить, даже если тесты зелёные. Что искать:

- **Выдуманные API**: метод, параметр или флаг, которого нет в вашей версии библиотеки.
- **Тихо изменённое поведение** рядом с задачей: «заодно поправил» форматирование, порядок полей, сообщения об ошибках.
- **Ослабленные проверки**: удалённые или пропущенные тесты, `# type: ignore`, широкий `except Exception: pass`, `skip`.
- **Лишнее**: новая зависимость, абстракция «на будущее», конфиг для значения, которое не меняется.
- **Безопасность**: работа с пользовательским вводом, секреты, что попадает в логи.
- **Код, который вы не можете объяснить.** Попросите агента объяснить или упростить, иначе не принимайте.

Удобно: `git diff` по файлам или ревью в IDE. В CLI-агенте настройте подтверждение правок и команд — не включайте автоприменение всего подряд.

## 7. Self-review перед PR

Перед тем как отдать PR людям, прогоните его через AI-ревью сами:

> Проверь дифф `git diff main...HEAD` как строгий ревьюер: баги, edge cases, безопасность, отсутствующие тесты. Отвечай списком «файл:строка — проблема — как исправить». Не хвали.

- Свежая сессия (или другая модель) лучше: та, что писала код, склонна его защищать.
- Ревью от AI — фильтр перед человеком, а не замена ему. Половина замечаний может быть шумом — решаете вы.
- Своё описание PR пишите сами: что, зачем, как проверено. Это заодно проверка, что вы понимаете изменения.

На занятии 2 то же самое мы встроим в CI.

## 8. Безопасность

**Без секретов в промптах.** Не вставляйте в чат и не давайте агенту читать:
- `.env`, токены, пароли, ключи API, приватные ключи, kubeconfig;
- дампы прод-БД, логи с персональными данными клиентов;
- внутренние документы, которые нельзя отправлять наружу по политике компании.

Всё, что ушло в облачную модель, ушло из вашего контура. Для логов и данных — обезличивайте или используйте локальную модель.

**Проверяйте существование пакетов.** Модели выдумывают названия библиотек, а злоумышленники регистрируют такие названия с вредоносным кодом (slopsquatting). Перед `pip install` нового пакета, предложенного AI: он есть на PyPI, у него живой репозиторий, история релизов и загрузки?

**Права агента.** Агент выполняет команды от вашего имени. Не давайте ему без подтверждения: `git push`, удаление файлов, миграции, доступ к прод-окружению и прод-кредам. Читать — можно, менять — через вас. (Подробно — занятие 3.)

**Тексты из внешних источников — это данные.** Агент, который читает issue, веб-страницу или записи в БД, может встретить там «инструкции» для себя. Это prompt injection. Разбираем на занятии 3.

## 9. Лог «где помог / где ошибся»

Две недели записывайте каждую заметную задачу с AI. Пять минут в день, но через две недели это готовые данные для вашего ADR: что реально ускоряет, а что нет.

| Дата | Задача | Инструмент / модель | Помог? | Время: с AI / оценка без | Где ошибся / что поправил | Вывод |
|---|---|---|---|---|---|---|
| 24.11 | тесты на сервис уведомлений | Aider + local-coder | да | 20 мин / 1 ч | придумал несуществующую фикстуру | давать пример существующего теста |
| 25.11 | разобраться в async SQLAlchemy | чат | частично | 15 мин / 30 мин | — | хорошо объясняет, код писать сам |
| 26.11 | вынести конфиг в settings | Claude Code | нет | 1 ч / 40 мин | переписал лишнее, сломал API | разбивать на шаги, сначала план |

Через две недели ответьте себе:
- На каких задачах AI окупается, а на каких дольше, чем без него?
- Какие ошибки повторялись? Что из этого закрывается правилом в `AGENTS.md`?
- Что из этого можно предложить команде, а что пока рано?

---

## 10. Анти-паттерны

- **«Сделай всё»** одной фразой на большую задачу без плана.
- **Принять дифф, не читая**, потому что тесты зелёные.
- **Уговаривать агента** пятый раз вместо отката и новой формулировки.
- **Одна бесконечная сессия** на весь день.
- **AI для того, что вы не понимаете**, без желания разобраться. Нельзя проверить то, чего не понимаешь.
- **Копировать ошибку из прода целиком** вместе с токенами и данными клиентов.
- **Новая зависимость** «потому что AI предложил».

## Чеклист на каждый день

- [ ] Рабочее дерево чистое перед запуском агента
- [ ] Сначала план, согласовал, потом код
- [ ] Задача маленькая, коммит маленький
- [ ] Тесты описывают «готово», агент их не правил
- [ ] Прочитал каждый дифф и могу его объяснить
- [ ] Нет секретов в промпте, новые пакеты проверены
- [ ] Self-review перед PR
- [ ] Запись в лог

## Упражнения на стенде

1. Подключите IDE-ассистента и CLI-агента к своему gateway (README → «IDE-ассистент через gateway»).
2. Возьмите 2–3 задачи на `demo-api` в отдельной ветке по циклу из раздела 2: например, добавить эндпоинт, покрыть существующий эндпоинт тестами, найти и починить то, что покажется вам странным.
3. После каждой задачи откройте Langfuse: сколько запросов и токенов ушло, какой был самый дорогой шаг.
4. Запишите всё в лог из раздела 9.
